# Redox side study — from ARM64 boot to a user-space file service

Redox and our kernel both boot on ARM64, manage physical pages, and take system calls from user mode. Their file paths show where their designs diverge. A Redox file operation can wake a server process and wait for its reply. Our planned Linux-style VFS calls a filesystem implementation inside the kernel. The parts worth carrying into M3 and M4 are the way register state crosses into Rust and the care needed when a kernel uses a user address.

## 1. What runs in the kernel, and what runs as a scheme?

**Redox.** A scheme is a named provider of operations such as open, read, and write. The kernel splits a path such as `debug:` at the colon, looks up the name in the caller's scheme namespace, and calls the provider. The resulting file descriptor records both the scheme ID and the provider's file number. The kernel itself provides `debug`, `irq`, `initfs`, and `proc`. It also initializes the ARM interrupt controller and timer. See `src/syscall/fs.rs:108-121`, `src/syscall/fs.rs:148-159`, `src/scheme/mod.rs:158-171`, and `src/arch/aarch64/device/mod.rs:10-21`.

A privileged process can register a scheme and keep a handle to serve it. Follow one write. The kernel's `UserScheme` makes the buffer available to the server. It queues a packet with a request ID and waits. The server reads requests and writes replies through its handle. The kernel uses the reply ID to wake the matching caller, then releases the buffer mapping. This lets a filesystem run in its own address space. The release's init script starts `redoxfs` as a process serving `file:`. See `src/scheme/root.rs:73-102`, `src/scheme/root.rs:165-195`, `src/scheme/user.rs:67-97`, `src/scheme/user.rs:257`, and `src/scheme/user.rs:334-339`. [Release init script, lines 29–38](https://gitlab.redox-os.org/redox-os/redox/-/blob/8f210bbab913bae7ae7b4a4b3183be33320e258c/initfs.toml#L29-38)

**Linux and our choice.** In Linux, `vfs_write` calls the open file's `write` or `write_iter` operation in the kernel (`fs/read_write.c:667-689`). Keep that model for our M5 ramfs, pipes, and `/dev/console`. A Rust trait can select the provider. An in-kernel call needs neither a server round trip nor a mapping of the caller's buffer into a second process.

## 2. ARM64 boot

**Redox.** The linker sets the entry to `early_init` and links the image high. The boot CPU receives the device-tree blob (DTB) address in `x0`. The entry code preserves it in `x19`, installs an exception vector base, disables translation, and builds early page tables. It loads the low and high table roots (`TTBR0_EL1` and `TTBR1_EL1`), enables the MMU, and branches to a high virtual address. Assembly sets the stack and passes Rust a `KernelArgs` record describing the image, stack, environment, and DTB. See `linkers/aarch64.ld:1-16`, `src/arch/aarch64/init/pre_kstart/early_init.S:30-50`, `src/arch/aarch64/init/pre_kstart/helpers/pre_mmu_enabled.S:3-51`, and `src/arch/aarch64/init/pre_kstart/helpers/post_mmu_enabled.S:28-38`, `src/arch/aarch64/init/pre_kstart/helpers/post_mmu_enabled.S:58-66`.

Rust's `kstart` finds the early serial port, reads the memory map, initializes the memory manager, paging, heap, and devices, then calls `kmain`. That function spawns a context which opens `debug:` for standard I/O and executes `initfs:/bin/init`. See `src/arch/aarch64/start.rs:36-73`, `src/arch/aarch64/start.rs:93-109`, `src/arch/aarch64/start.rs:126-152`, `src/lib.rs:174-199`, and `src/lib.rs:210-232`.

**Linux and our choice.** Linux builds an early identity map with a C helper, enables the MMU, then maps and relocates the kernel before entering `start_kernel` (`arch/arm64/kernel/head.S:85-94`, `arch/arm64/kernel/pi/map_range.c:91-102`, `arch/arm64/kernel/head.S:508-522`, `arch/arm64/kernel/head.S:243-247`). Our Image entry saves the DTB, sets the stack, and clears BSS before Rust. Rust builds memblock and turns on the MMU in `paging_init` (`foundation/src/arch/aarch64/head.rs:14-46`, `kernel/src/init/main.rs:61-74`). Keep that tested boot path for M3. Revisit the high-linked image for M4, when each process needs a low-half address space of its own. Our current executable image still uses the low identity map (`klib/src/mm/layout.rs:77-92`).

## 3. Page tables, physical frames, and the heap

| Layer | Redox OS 0.7.0 | Linux v7.3 | Our M2 implementation and what to keep |
|---|---|---|---|
| Page tables | Four levels and 4 KiB pages. After the assembly boot tables, a bump allocator supplies a fresh table. Redox maps RAM and the high kernel image, then activates the table. See `rmm/src/arch/aarch64.rs:14-17`, `src/arch/aarch64/rmm.rs:106-134`, `src/arch/aarch64/rmm.rs:138-148`, and `src/arch/aarch64/rmm.rs:169-180`. | Memblock supplies early table pages. ARM64 `paging_init` installs the RAM mappings. See `arch/arm64/mm/mmu.c:107-116` and `arch/arm64/mm/mmu.c:1474-1481`. | Keep the low image mapping and high linear map for M3. Our high alias of kernel text and read-only data also stays read-only. See `klib/src/mm/layout.rs:86-92`. |
| Physical frames | RMM hands the bump allocator to a type called `BuddyAllocator`. In this revision it scans per-page usage counts for a contiguous run of the requested length and zeroes each allocated page. Freeing decrements the counts and updates the next search position. See `src/arch/aarch64/rmm.rs:176-180` and `rmm/src/allocator/frame/buddy.rs:184-225`, `rmm/src/allocator/frame/buddy.rs:245-272`. | The buddy allocator searches free lists by order. It splits a larger block to allocate and merges free buddies on return. See `mm/page_alloc.c:1901-1916`, `mm/page_alloc.c:960-970`, and `mm/page_alloc.c:1005-1009`. | Keep our order-based allocator. It follows the Linux algorithm, and a caller returns an owned `Pages` value carrying its original order. See `Cargo.toml:46-58`, `src/allocator/mod.rs:3-37`, and `src/allocator/linked_list.rs:8-29`. | Boot releases memblock's free pages to the page allocator, then initializes SLUB's object caches. See `mm/mm_init.c:2668-2672` and `mm/slub.c:8644`. | Keep slab size classes for small objects and buddy blocks for larger or more highly aligned allocations. The two paths are visible in `foundation/src/mm/heap.rs:96-111`. |

## 4. Where unsafe Rust lives

**Redox.** Low-level operations have wrappers in several parts of the kernel. RMM locks its frame allocator around allocation and free. Exception entry turns a raw stack pointer into a Rust reference. The syscall module checks user-page permissions before making slices. A comment there identifies the limit of that check: another user thread can still access the same memory. A mapped page alone cannot establish the exclusive access a Rust mutable reference promises. See `src/arch/aarch64/rmm.rs:183-207`, `src/arch/aarch64/interrupt/handler.rs:296-308`, and `src/syscall/validate.rs:6-31`, `src/syscall/validate.rs:77-90`.

**Linux and our choice.** Linux's Rust `UserSlice` stores an address and length. Reads and writes go through the kernel's user-copy routines, which check access at the time of the operation (`rust/kernel/uaccess.rs:149-167`). Keep our crate boundary. `foundation` documents and checks its unsafe operations, while `kernel` and `klib` forbid them (`foundation/src/lib.rs:5-10`, `kernel/src/lib.rs:8`, `klib/src/lib.rs:5`). For M3's first `write`, I recommend copying bytes into a bounded kernel buffer in `foundation`. The console then borrows kernel-owned bytes. Redox uses external memory, locking, and parsing crates (`Cargo.toml:16-27`, `Cargo.toml:38-40`). Our implementation can keep using only the workspace crates, `core`, and `alloc`.

## 5. Task switching

**Redox.** The scheduler takes a global switch lock, updates contexts, and searches by context ID, wrapping at the end. It selects a runnable context assigned to this CPU, marks which context is running, and hands the two architecture states to `switch_to`. The ARM64 code transfers register state, changes the user page-table root and flushes the TLB if the root changed, then switches kernel stacks. A finish hook releases the old and new context locks from the resumed stack. The reason for the hook is concrete: after loading the new stack, local guards belong to the suspended call. See `src/context/switch.rs:90-107`, `src/context/switch.rs:126-157`, `src/context/switch.rs:165-182`, `src/context/switch.rs:197-215`, `src/context/arch/aarch64.rs:283-287`, `src/context/arch/aarch64.rs:352-380`, and `src/context/switch.rs:71-85`.

**Linux and our choice.** Linux picks a task from the run queue, changes the address space as needed, then calls the architecture switch. ARM64 `cpu_switch_to` saves and restores the callee-saved registers, stack pointer, and return address. See `kernel/sched/core.c:7199`, `kernel/sched/core.c:7284`, `kernel/sched/core.c:5512`, `kernel/sched/core.c:5533`, and `arch/arm64/kernel/entry.S:817-843`. Our scheduler is planned for M4. Keep task selection in safe Rust and give `foundation` the machine-state switch. Document which stack owns each guard at the handoff. Test resumption by giving two tasks different register values across timer preemption.

## 6. ARM64 system-call entry

| ABI detail | Redox OS 0.7.0 | Linux ARM64 and our M3 target |
|---|---|---|
| Entry and return | `svc 0`, number in `x8`, up to five arguments in `x0–x4`, result in `x0`. See `syscall/src/arch/aarch64.rs:12-34`. | Number in `x8`, up to six arguments in `x0–x5`, result in `x0`. See `arch/arm64/kernel/syscall.c:138-141`, `arch/arm64/include/asm/syscall.h:58-62`, and `arch/arm64/include/asm/syscall.h:80-90`. |
| Call numbers | `write = 0x21000004` encodes the file and slice classes. `exit = 1`. See `syscall/src/number.rs:1-7`, `syscall/src/number.rs:23`, and `syscall/src/number.rs:45`. | `write = 64` and `exit = 93`. See `scripts/syscall.tbl:83` and `scripts/syscall.tbl:120`. |

**Redox.** A synchronous exception from EL0 enters the vector and saves registers on the kernel stack. Rust checks the exception class in `ESR_EL1`. For a system call, it dispatches using the saved registers and writes the result into the saved `x0`. The assembly wrapper restores state and executes `eret`. In this release, the same handler prints diagnostics and loops on other synchronous EL0 exceptions. See `src/arch/aarch64/init/pre_kstart/helpers/vectors.S:66-71`, `src/arch/aarch64/interrupt/handler.rs:310-326`, `src/arch/aarch64/interrupt/exception.rs:26-54`, and `src/arch/aarch64/interrupt/syscall.rs:57-62`.

**Linux and our choice.** Linux routes SVC, data aborts, and instruction aborts to distinct handlers. The syscall path bounds-checks the number before indexing its table (`arch/arm64/kernel/entry-common.c:771-784`, `arch/arm64/kernel/syscall.c:38-54`). Our M2 vectors report the fault and power off (`foundation/src/arch/aarch64/vectors.rs:15-28`, `foundation/src/arch/aarch64/vectors.rs:86-92`). For M3, keep the Linux ABI and its separate user-fault path. Have the assembly entry save the frame before calling Rust. A safe dispatcher only needs the decoded number, arguments, and a way to set the return value.

## Open questions

1. For M3's `write`, should we introduce a small user-to-kernel copy operation now, or bring the full M4 `UserPtr` interface forward? I recommend the small operation. It gives the first syscall a clear ownership boundary while leaving process address spaces to M4.
2. For M4, should the two-task preemption test check distinct callee-saved register values, or only check that both tasks print? I recommend checking the registers as well. Interleaved output alone could pass even if a resumed task gets the other task's register value.
